## 3. Component Architecture

### 🧠 Design Philosophy

The system follows a **pipeline + resilience + multi-tenancy** pattern:
1. **Data flows one way** (ESP32 → MQTT → Backend → DB → Frontend)
2. **Every step has a fallback** — if ML fails, data still gets stored. If MQTT drops, the ESP32 buffers readings.
3. **Validation happens at the edges** — schema validation rejects bad data before it reaches the ML model.
4. **Users are isolated** — each user claims one device, and the dashboard only shows data from that device.
5. **Auth is stateless** — JWT tokens in `localStorage`, verified on every API call.

### 🔌 ESP32 Firmware Components

#### `TaskSensorPoll()` (Core 0)
- **What it does:** Reads voltage, current, power, and power factor from the PZEM-004T sensor every 1 second.
- **Why it matters:** This is your data source. Without it, nothing flows.
- **Key behavior:** Uses `sensorMutex` to safely share data with Core 1. Feeds the hardware watchdog timer (WDT) after every successful read.

#### `TaskMqttAndInference()` (Core 1)
- **What it does:** Takes sensor data, computes derived features, normalizes them with RobustScaler, runs the Isolation Forest model, and publishes anomalies via MQTT.
- **Key behavior:** Uses a state machine (`STATE_WIFI_CONNECTING` → `STATE_MQTT_CONNECTING` → `STATE_ONLINE` → `STATE_RECOVERING`) to handle network drops gracefully.

#### `pushToBuffer()` / `popFromBuffer()` / `drainBuffer()`
- **What they do:** Store up to 120 readings when MQTT is offline, then send them all at once when the connection returns.

---

### 🐍 Python ML Pipeline Components

#### `EnergyTelemetry` (Pydantic Model in `mqtt_schema_validator.py`)
- **Fields:** `device_id`, `timestamp`, `V`, `I`, `P`, `PF`, `Q`, `alert`, `score`, `buffered`
- **Validation rules:** Voltage: 100–300 V, Current: 0–100 A, Power Factor: 0.0–1.0
- **Why it matters:** Catches corrupted or spoofed data before it pollutes your database or ML model.

#### `MLInferenceService` (Singleton in `ml_inference_service.py`)
- **What it does:** Loads `isolation_forest_model.pkl` once at startup, then runs `predict()` on every incoming record.
- **Key methods:**
  - `predict(record)` → returns enriched record with `anomaly_score` and `is_anomaly` flags
  - `predict_batch(records)` → efficient batch inference
  - `health()` → reports service status, inference count, error count
- **Degraded mode:** If the model file is missing or corrupt, the service logs a CRITICAL error but continues operating. Data ingestion never stops.

### Step-by-Step Journey

```
┌─────────────┐     ┌─────────────┐     ┌─────────────────┐     ┌─────────────┐     ┌─────────────┐
│   ESP32     │     │ MQTT Broker │     │  FastAPI Backend│     │   SQLite    │     │   Browser   │
│  (Edge)     │────▶│  (Mosquitto)│────▶│   (main.py)     │────▶│   (User     │     │  (React/    │
│             │     │             │     │                 │     │   Data)     │     │   Vanilla)  │
└─────────────┘     └─────────────┘     └─────────────────┘     └─────────────┘     └─────────────┘
       │                    │                     │                      │                  ▲
       │                    │                     │                      │                  │
       ▼                    ▼                     ▼                      ▼                  │
  1. Sensor Read      2. MQTT Publish      3. Schema Validate      4. Persist User     8. Render
  2. Feature Eng.     3. Topic Routing     4. ML Inference            + Device          9. Chart
  3. Edge Inference   4. QoS 0/1           5. In-Memory Store      5. Query Device      10. Alert
  4. JSON Payload                          6. WebSocket Broadcast     Status
                                           7. Device Filter
```

### Device Isolation Flow

1. User logs in → receives JWT
2. User claims device → `device_id` stored in SQLite linked to `user_id`
3. Dashboard loads → `authGuard()` fetches `/device/status`
4. WebSocket connects → all ESP32 readings broadcast to all clients
5. Frontend filters → `if (msg.device_id !== window.userDeviceId) return;`
6. **Result:** User only sees data from THEIR device, even in multi-tenant deployments

## 6. What Happens When Things Go Wrong?

| Failure Point | System Response |
|---------------|-----------------|
| **ESP32 can't reach MQTT broker** | Readings stored in async circular buffer (up to 120). When WiFi returns, `drainBuffer()` sends queued readings. |
| **MQTT broker is down** | Backend logs warning, retries with exponential backoff. |
| **InfluxDB is down** | `write_to_influxdb()` catches exception, returns `False`. Reading still kept in memory and broadcast. |
| **ML model file is missing** | `MLInferenceService` enters **degraded mode**. Data ingestion continues, no anomaly scores. |
| **Browser disconnects** | WebSocket closes. Auto-reconnects every 3s. Server sends last 20 readings as catch-up. |
| **Corrupted JSON arrives** | `mqtt_schema_validator.py` rejects it. Logged and discarded. No crash. |
| **JWT expires/invalid** | Frontend `authGuard()` redirects to `/login`. Token removed from `localStorage`. |
| **User tries to claim second device** | Backend returns 400: "User already has a claimed device". Must unclaim first. |
| **Dashboard accessed without device** | `authGuard()` redirects to `/claim` page automatically. |

## 8. Database Schema

```sql
-- users table
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    email VARCHAR(255) UNIQUE NOT NULL,
    hashed_password VARCHAR(255) NOT NULL,
    full_name VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- devices table (one per user)
CREATE TABLE devices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL UNIQUE,
    device_id VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- appliances table (many per user)
CREATE TABLE appliances (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    name VARCHAR(255) NOT NULL,
    wattage REAL NOT NULL,
    quantity INTEGER DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```
